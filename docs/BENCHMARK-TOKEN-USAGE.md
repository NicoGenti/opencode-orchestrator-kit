# Token Usage Benchmark Protocol

This document defines a reproducible A/B protocol to measure the token impact of the repo map and search ladder on exploration tasks. Numbers produced this way are **project-specific and operational**, not scientifically validated benchmarks.

## Setup

1. Pick a fixed task set (3-5 exploration questions of similar difficulty, e.g. "find all callers of X", "explain the auth flow", "locate config for Y").
2. Run each task twice on the same repo state:
   - **A (control):** `.context/repo-map.md` absent (rename it temporarily).
   - **B (treatment):** `.context/repo-map.md` present (generated by `profiler`).
3. Use the same model tier (`TIER_FAST`) and the same explorer depth (`medium`) for both runs.

## Metrics to record

For each run, capture:

- Number of tool calls (`rg`, `find`, `sg`, CRG, reads).
- Total characters/lines read (sum of `wc -l` or read slices).
- Number of findings in the final report.
- Wall-clock time.
- Token usage if the provider exposes it (input + output tokens per call).

## Recording template

| Task | Run | Repo map | Tool calls | Lines read | Findings | Tokens (in/out) | Notes |
|---|---|---|---|---|---|---|---|
| T1 | A | no |  |  |  |  |  |
| T1 | B | yes |  |  |  |  |  |

## Interpretation rules

- Compare A vs B per task, not as a single aggregate.
- A reduction in lines read with the same or better findings count is the primary success signal.
- Do not cherry-pick: report all tasks, including ones where the repo map did not help.
- Repeat the protocol at least twice before drawing conclusions.

## Caveats

- Results depend on repo size, language, and task type.
- This is an operational engineering metric, not a scientific benchmark.
- Do not publish numbers without stating the repo, task set, and run count.
