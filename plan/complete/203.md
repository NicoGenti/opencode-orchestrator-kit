## Goal

Implement issue #203 by preventing the orchestrator from spawning duplicate or self-parallel subagent dispatches for the same task, and by removing unsafe concurrent-write capabilities from worker agents. The accepted design uses `.context/progress.md` as the single source of dispatch accounting, denies destructive git operations to every worker, and reserves destructive or authorization-sensitive actions for the user.

## Success Criteria

- `test-engineer` cannot invoke any `git` subcommand (`permission.bash` denies `git *`).
- `test-engineer` retains exactly the five read-only bash allows added to its permission matrix.
- The orchestrator's primary and quick prompts include a `### Dispatch guard` subsection that reads `accepted=<runtime-id>/<task-key>` entries from `.context/progress.md` and suppresses duplicate or self-parallel dispatches.
- A focused test file `tests/dispatch-guard.test.ts` verifies the guard behavior and the updated permission matrix.
- `CHANGELOG.md`, `.context/decisions.md`, and `.context/issues.md` contain concise, accurate records.
- All mirrored agent assets under `plugin/assets/` stay byte-identical with their sources.

## Scope

### Phase A — `test-engineer` permission hardening

1. Update `agents/test-engineer.md` `permission.bash` block:
   - Add `git *: deny`.
   - Add the five agreed read-only allows.
   - Raise the permission character budget from 3800 to 4100.
2. Update `tests/permission-matrix.test.ts` expectations for the new deny/allow rows.
3. Refresh any agent-instruction snapshot tests that cover the `test-engineer` prompt.
4. Run `bun run sync-assets` so `plugin/assets/agents/test-engineer.md` mirrors the source.

### Phase B — Orchestrator dispatch guard

1. Edit `agents/orchestrator.md`:
   - Add a `### Dispatch guard` subsection under the dispatching guidance.
   - Require reading `.context/progress.md` and checking for an existing `accepted=<runtime-id>/<task-key>` entry before delegating.
   - Suppress the dispatch when the same runtime ID and task key is already accepted/in-flight; surface a concise note to the user instead.
2. Apply an equivalent clause to `agents/orchestrator-quick.md`.
3. Add a mirror bullet to `AGENTS.md` documenting that destructive git actions are denied to every worker and only the user may authorize them.
4. Trim excess wording in touched prompts to stay within the character budgets enforced by `tests/workflow-hardening.test.ts`.
5. Run `bun run sync-assets` to mirror updated prompts and `AGENTS.md`.

### Phase C — Tests, changelog, and session-memory records

1. Create `tests/dispatch-guard.test.ts` covering:
   - Duplicate suppression when `accepted=developer-fixer/some-task` exists.
   - Self-parallel suppression for the same `<runtime-id>/<task-key>`.
   - Allowed dispatch when the task key or runtime ID differs.
   - `test-engineer` `git *: deny` and the five read-only allows.
2. Add a `CHANGELOG.md` bullet under `[Unreleased]` summarizing the duplicate-dispatch guard and permission hardening.
3. Append the decision to `.context/decisions.md`: reject JSONL dispatch sink; use `.context/progress.md` accounting; deny destructive git to every worker; only user can authorize destructive actions.
4. Append the resolution to `.context/issues.md` for issue #203.

### Structural Impact

- **Primary modules/files**: `agents/test-engineer.md`, `agents/orchestrator.md`, `agents/orchestrator-quick.md`, `AGENTS.md`, `tests/permission-matrix.test.ts`, `tests/dispatch-guard.test.ts`, `CHANGELOG.md`, `.context/decisions.md`, `.context/issues.md`.
- **Affected callers/dependents**: The orchestrator prompts are consumed by the runtime as primary entry points; changes affect how every subagent delegation is authorized. `test-engineer` callers lose all `git` capabilities, so any existing flow that relied on `git` from that agent must be handled by the user or another explicitly authorized path.
- **Likely test surface**: `tests/permission-matrix.test.ts`, `tests/workflow-hardening.test.ts`, `tests/dispatch-guard.test.ts`, `tests/plugin-assets-parity.test.ts`.
- **Phase order**: Phase A before Phase C (tests depend on hardened permissions); Phase B before Phase C (dispatch-guard tests depend on prompt text). Phase A and Phase B are independent and may be sequenced in either order.
