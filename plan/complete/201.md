## Goal

Deliver a pinned, baseline-driven NVIDIA SkillSpector v2.13.6 supply-chain scan covering the kit's full prompt surface (`skills/`, `agents/`, `extras/`, `command/`), integrated as a fail-closed gate in the existing CI workflows, with a committed, reviewed root baseline and documented consumer guidance.

## Success Criteria

1. `skillspector scan` runs in CI on every PR and every `main` push via `.github/workflows/test.yml` (no new workflow file), using SkillSpector **v2.13.6** and the committed `.skillspector-baseline.yaml` at repo root.
2. The scan covers the full shipped prompt surface: `skills/` + `agents/` + `extras/` + `command/`.
3. The baseline records the SkillSpector version and commit used to generate it, and a deliberate re-triage procedure is documented for tool upgrades.
4. CI fails on any new finding not in the baseline (`--baseline .skillspector-baseline.yaml --fail-on-findings`); the docs explain how to re-baseline safely.
5. README/docs contain a "verify your skills" section with install → scan → baseline → verdict flow, companion (`web-*`) and `project-*` skill guidance, and a fail-closed consumer check recommendation.
6. No runtime behavior change to agents or plugin; no new npm dependencies; `bun test` green; existing workflow-set pins untouched; no new workflow file added.
7. Initial false-positive triage is committed as part of the PR, with each suppressed finding mapped to a reason rather than blanket-accepted.

## Inputs Available

- **Scanner CLI** (verified): `skillspector scan <path> --no-llm`; format `-f [terminal|json|markdown|sarif]`, file via `-o PATH` (file output unavailable on Windows — POSIX-only; stdout works). Baseline: `skillspector baseline <path> -o .skillspector-baseline.yaml` (default output filename is `.skillspector-baseline.yaml`); delta mode is `scan --baseline .skillspector-baseline.yaml`. Exit codes: 0 = score ≤50; 1 = score >50 or `--fail-on-findings` on any active finding; 2 = error/malformed baseline. Default exit is weak (one CRITICAL = +50 = score 50 = exit 0), so use `--fail-on-findings` with baseline. Flags available: `--show-suppressed`, `--use-shipped-baseline`, `--recursive`, `--max-skills N`, `--exclude GLOB`, `--fail-on-incomplete`, `--min-coverage PERCENT`, `-V/--verbose`. SC4/OSV live lookup runs even with `--no-llm`, needs `api.osv.dev`, no disable flag; it falls back to bundled static list offline.
- **CI context** (verified): workflow set = 6 files; trigger-pin tests stay untouched because no new file is added. `test.yml:3-6` triggers push to `main` + all PRs; `test.yml:21-38` sets up Python 3.12 + `python` alias; `release.yml:115-132` has the same Python block. ## Notes / Edge Cases

- **Issue traceability / scope deviation**: The issue originally leaned toward scanning "skills only." The user explicitly expanded coverage to `skills/` + `agents/` + `extras/` + `command/`. If Phase 0 shows the scanner does not meaningfully cover non-`SKILL.md` content, the implementer must document the residual coverage gap and re-confirm the narrower surface before committing the baseline.
- **OSV flakiness posture**: `--no-llm` still attempts live OSV lookups against `api.osv.dev`. The scanner falls back to a bundled static list when offline. The plan accepts this residual network dependence; no retry wrapper is required, but CI flakiness should be monitored and documented in the docs page if observed.
- **Dependabot and uv action pin**: If `astral-sh/setup-uv` is used, Dependabot will auto-bump the `uses:` ref. This is acceptable because it is an action ref, not the SkillSpector version; the SkillSpector version itself is pinned to tag `v2.13.6`. Document that the action pin is managed by Dependabot while the tool version is managed by the baseline re-triage procedure.
- **`workflow_dispatch` decision**: Adding `workflow_dispatch` to `test.yml` for baseline-regeneration runs is allowed because the trigger-pin tests only forbid `issues:` / `issue_comment:` triggers. If added, it must not weaken the push/PR gate.
- **Baseline re-triage procedure**: Tool upgrades require a deliberate baseline regeneration and review. The baseline file must record the new version and commit; the PR that upgrades the tool must include the regenerated baseline diff as a reviewed change, not an unattended CI artifact.
- **Windows verification limitation**: Local scanner file output is unavailable on Windows. The developer-fixer may verify the scan via stdout redirect, CI artifacts, or WSL; the local Bun-based gates (`bun test`, `lint`, `format:check`, `sync-assets --check`, `build`) must still pass natively.
