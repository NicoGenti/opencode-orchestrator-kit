## Goal

Add a bounded, automatic lesson-recall step at planning time so the orchestrator consults a slice of past decisions, issues, design rules, and completed-plan frontmatter before creating a plan card; the planner receives the slice as input, and the orchestrator records what was recalled in `.context/progress.md` and in the completed plan's frontmatter, without changing `/recall` semantics.

## Success Criteria

1. **AC1 — automatic consult on non-trivial tasks**: before delegating to `planner`, the orchestrator reads the bounded slice from the approved sources with no manual command; the no-match path is grep/index-scan only.
2. **AC2 — caps documented and enforced**: ≤3 plans from `plan/complete/*.md`, ≤2k token total, each plan reduced to ~30 lines (frontmatter + Goal + Scope + outcome); `.context/progress.md` carries a pointer line stating what was recalled.
3. **AC3 — `/recall` isolation invariant preserved**: no auto-trigger, no bootstrap read, no access to `.context/comprehension-log.md`, `.context/research-dataset.jsonl`, `.context/triage-dataset.jsonl`, or `.context/comprehension/**`; pinned by existing tests.
4. **AC4 — optional `tags`/`outcome`**: frontmatter keys are documented in `plan/README.md` and `AGENTS.md`, tolerated by `plan_board check` with no new warning, and existing plans validate unchanged.
5. **AC5 — green gates and docs**: `bun test` + V1↔V2 parity stay green; `README.md` and `docs/CONFIGURATION.md` describe the recall step as a distinct mechanism from `/recall`.

4. Missing `tags`/`outcome` stays silent in `plan_board check` (no WARN; 13 existing cards lack them).
5. The automatic `outcome` write must not change the `comprehension-unrecorded` refusal semantics.

## Notes / Edge Cases

- **Outcome mechanism**: recommend a **caller-supplied optional string flag** `--outcome` on `move`, written only when `--to complete`. Justification: the orchestrator owns the recall trigger and already knows the pointer value, so a stateless board tool stays scoped to the board root; a server-derived value would require the tool to read `.context/progress.md`/session memory, violating isolation. V1 impact: add `outcome` to `FM_KEYS`, add `--outcome` arg, write it in `update_status`, include it in the `cmd_move` payload. V2 + tool impact: mirror in TS, add `outcome` to `PLAN_BOARD_TOOL_INPUT.properties` and to `STRING_FLAG_FIELDS`.
- **Budget headroom**: `agents/orchestrator.md` is at 23,979/24,000 chars. If the new section exceeds the cap, either trim ≥21 chars of prose elsewhere in the same file or deliberately raise `tests/workflow-hardening.test.ts:85` in the same commit.
- **Agent frontmatter guard**: `tags`/`outcome` must not appear as keys in `agents/` or `extras/` frontmatter (`tests/frontmatter-order.test.ts:119-140`); they are board-only keys.
- **`/recall` wording guard**: the sentence "Manual invocation only. Nothing in this profile may trigger `/recall` automatically." must remain the only sentence about `/recall` triggering; the new section must use verbs like "consult"/"grep"/"read" and explicitly exclude `/recall` files.
- **Existing cards**: the 13 plans lacking `tags`/`outcome` must produce no new `plan_board check` warnings.
- **Progress pointer**: use the recency rule — the latest dated decision supersedes older ones; the pointer line cites source files and dates, not full text.
- **Windows/CRLF verification**: targeted test files are the signal; accept the known ~25 ambient fails and verify parity against CI-equivalent LF blobs when needed.
